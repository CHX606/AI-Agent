# Bit Agent 产品说明与当前范围

更新日期：2026-09-09。本文说明项目想解决什么问题，以及哪些部分已经有代码实现。早期“按 Day 1、Day 2 开发”的计划不再作为当前进度。

## 这个项目要帮你做什么

给它一个代码项目和一个明确的问题，例如“这个计算函数结果不对，帮我修复”，它应该能找到相关文件、理解问题、修改代码，并把检查结果和修改过程交给你。

它面向需要处理代码问题的开发者，也用于我们自己研究 Agent 怎样调用工具、怎样判断任务是否完成。

## 用户能怎么使用

- Desktop：通过桌面窗口选项目、输入任务、看执行事件和结果，浏览项目文件。
- CLI：在终端提交、查询、取消任务。
- Gateway API：由其他程序通过 HTTP 接入同一套任务服务。
- Python 接口：直接调用单 Agent 或 Multi-Agent，适合开发和评测。

## 当前已经有实现的能力

| 能力 | 实际作用 | 主要位置 |
| --- | --- | --- |
| 任务接收、排队、查询和取消 | 把用户请求交给执行服务 | `apps/gateway`、`services/agent/src/bit_agent/runtime` |
| 仓库结构和代码检索 | 帮 Agent 找到要看的代码 | `context` |
| 基础工具及本地交互工具 | 查看、修改、按项目验证、提问和只读分工 | `tools`、`runtime/application/delegation.py` |
| 动态工具循环 | 模型根据每次工具结果决定下一步 | `agent/runtime.py` |
| 多 Agent 调查 | 主 Agent 按三档模式决定是否叫只读帮手 | `runtime/application/delegation.py`，旧实现保留于 `multi_agent` |
| 当前任务记忆 | 记录目标、读过的文件、改动和验证状态 | `memory/working.py` |
| 长期记忆和向量检索 | 保存并召回通过审核的经验 | `memory`，需要配置和接入 |
| 上下文压缩 | 避免历史内容不断膨胀 | `context/manager.py` |
| Docker 沙箱 | 在隔离环境中执行测试和检查 | `sandbox`、`infra/sandbox` |
| 独立评测与执行事件 | 保存证据，检查 Agent 是否真把题做对 | `evals`、`observability` |
| 桌面与命令行入口 | 让用户不必直接写 Python 调用代码 | `apps/desktop`、`cli.py` |

长期记忆和向量数据库已经不属于“完全没做”的功能。它们有实现和接入接口，但默认本地 AgentRuntime 没有自动装配 PostgreSQL 召回和记忆巩固。

## 当前不应承诺的能力

- 完整的独立 Web 管理后台。
- 生产级用户认证、租户隔离、配额和部署运维方案。
- IDE 插件。
- 任意语言、任意规模仓库都能自动修好。
- 任意 Shell 命令执行。
- 每次任务都一定能成功，或已有实现一定没有 bug。

默认本地工具按项目选择 Python 或 npm/pnpm 单包的验证方式。多包工作区、私有依赖和缺少测试的项目不能宣称自动验证通过，支持范围见 [功能说明](PRODUCT_HARDENING.md)。

## 一次任务的正常过程

1. 用户选择工作区并描述任务。
2. Gateway 检查请求格式，直接交给本机 Python AgentRuntime。
3. AgentRuntime 恢复 SQLite 会话，按工作区锁和并发名额安排执行。
4. 主 Agent 按多 Agent 模式决定是否叫只读帮手，不额外调用分类模型。
5. 框架先检查权限，需要时等用户确认，然后修改文件并保存快照。
6. 修改后运行测试和静态检查；失败时读取反馈继续处理。
7. 保存结构化结果、修改文件列表和执行事件。
8. 客户端显示结果，用户查看实际完成情况。

这里的“规划、执行、验证”描述的是工作过程，不保证每个阶段都对应一个单独的类或一个固定状态枚举。

## 怎么理解“完成”

`COMPLETED` 是一次运行的状态，不是对整个产品质量的永久保证。

发生代码修改时，默认本地框架要求与实际项目语言对应的测试和质量检查成功，才允许直接结束。Multi-Agent 还会区分子任务是否都完成、汇总是否有冲突，可能返回 `PARTIAL`。

独立 EvalRunner 会另外执行验收测试、比较文件快照，并检查是否动了不允许修改的文件。评测得到的 Diff 是文件差异证据；普通任务可通过改动审阅接口查看前后差异；它仍不等同于独立评测报告。

## 后续开发关注什么

完善功能、修复实际 bug、增加有意义的验证用例，并把真实运行中的限制写清楚。涉及生产部署和新的语言工具链时，需要相应实现和验证，不能只修改文档里的状态。
