# SDK 主线与学习入口

更新日期：2026-09-09。

## 先记住这一条主线

```text
你选择文件夹、发送消息
    ↓
桌面 → Gateway → 本地 AgentRuntime
    ↓
恢复这段对话的历史、目标和文件修改状态
    ↓
OpenAI Agents SDK Runner
    ├─ 请求模型
    ├─ 模型要求使用工具 → SDK 调用对应工具
    ├─ 工具结果交回模型 → SDK 继续下一轮
    └─ 模型给出最终回答
    ↓
产品检查是否还在等用户、是否还有未验证修改
    ↓
保存到本机 SQLite，并把事件和回答显示在桌面
```

以前我们自己写“请求模型、找出工具调用、逐个执行、继续请求”的循环。
现在这一整套调度交给 `openai-agents`，不是在旧循环外面套一层 SDK。

## 这次实际替换了什么

| 原来自己维护的部分 | 现在谁负责 |
| --- | --- |
| 模型与工具之间反复执行的循环 | SDK `Runner.run` / `Runner.run_streamed` |
| 把工具注册给 Agent、执行模型提出的调用 | SDK `Agent` 和 `FunctionTool` |
| 流式响应的解析和最终结果整理 | SDK；产品只把文字事件转发到界面 |
| 工具并发数量 | SDK `ToolExecutionConfig`，当前同一主 Agent 一次只执行一个工具 |
| 成功和失败各复制一份结果组装代码 | 合并为一个 `finish_result` |

依赖固定为 `openai-agents==0.22.1`，OpenAI 客户端范围为 `>=3.3,<4`。
旧的 `bit_agent/llm/streaming.py` 已移除，不再保留另一套流式解析实现。
主 Agent 和本地只读子 Agent 都经过同一个 SDK 执行入口。

## 为什么仍有一些我们自己的代码

SDK 能调用工具，但不知道这个桌面软件对用户作过什么承诺。
以下是产品规则，不应为了少几行代码直接删掉：

| 保留的部分 | 大白话解释 |
| --- | --- |
| 文件权限和审批 | 用户没批准，模型即使提出写文件也不能执行。 |
| 暂停、补充、修改目标 | 用户改了要求，就跳过还没执行的旧工具计划。 |
| 问题与超时选择 | 普通偏好可以超时用推荐项；高风险操作不能超时批准。 |
| 修改后验证 | 模型说“做完了”不等于代码确实已经验证。 |
| 取消时等待工具收尾 | 任务显示取消后，不能还有工具在后台继续写文件。 |
| SQLite 和文件修改记录 | 保存对话、事件、审批和补丁，以便重启后继续或审阅撤销。 |
| 上下文压缩策略 | 保留现有的大结果外置、摘要、关键状态纠偏和输入预算规则。 |

`ProductHooks` 就是 SDK 给产品的通知入口，不是另一套 Agent 框架。
SDK 拿到模型结果后通知它；它只负责保存计划、检查用户的新要求和验证条件。

代码中仍有两处需要继续处理的循环：一处是在摘要期间收到新要求后重新准备输入；
另一处是在用户修改要求或代码尚未验证时拒绝结束。这两处都不自行调用模型或遍历执行工具，工具循环仍由 SDK 管。

## 哪些并没有在这轮替换

- MCP 连接原本就用官方 `mcp` 库，并不是我们从零实现通信协议，因此没有再造一份适配器。
- RepoMap、AST 索引、搜索和片段选择仍保留。它们是代码检索功能，不会因为安装 Agent SDK 就自动获得同等行为。
- Context Manager 和长期记忆仍保留。没有把现有的多来源摘要纠偏和工具证据规则冒充成 SDK 自带能力。
- 旧 Redis、Worker 和旧多 Agent 编排模块没有批量删除；它们不是本次默认桌面运行主线的替代后备循环，也不要求桌面用户启动。

这次没有额外引入 LangGraph，也没有同时叠加另一套 Agent 编排框架。

## 接下来怎么读代码

先读主线，不必从每个文件第一行一直读到最后一行。

1. `services/agent/src/bit_agent/runtime/application/service.py` 的 `_execute`：一次桌面任务从哪里进入 Python。
2. `services/agent/src/bit_agent/agent/runtime.py` 中的 `Agent(...)`、`RunConfig(...)` 和 `Runner.run_streamed(...)`：我们给 SDK 配了模型、工具和哪些产品规则。
3. 同一个文件的 `invoke_tool`：SDK 调用工具后，我们怎样保存结果、更新工作记忆。
4. 选择一个实际工具，例如 `tools/read_file.py`，跟着它的输入和输出走一遍。
5. 真正想了解暂停、摘要或撤销时，再分别进入对应模块。

现在你不需要去读 `.venv/Lib/site-packages/agents` 中 SDK 内部的每个函数。
应用开发先掌握“传入什么、返回什么、在哪保存、失败如何处理”，比逐行背实现重要。

## 数据和模型服务的边界

- SDK 在用户电脑的 Python 进程里执行，不会因为引入 SDK 就多出一台云端 Worker。
- 仍使用应用设置中的模型地址、模型名称和密钥；这里保留的是 Responses API 接口，不承诺任何非兼容接口都能直接使用。
- 会话仍在本地保存，不依赖 OpenAI 的服务端会话 ID。
- 关闭 SDK 的额外 tracing 上传，并设置 `store=False`。模型请求本身仍需要发送到用户配置的模型服务，这不是离线大模型。
