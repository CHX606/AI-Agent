# 2026-10-01 生产力改进验证记录

这一轮按“先修走不通的场景，再补常用功能”的顺序改进，共 10 个提交（`4eb3221` 到 `f8be912`）。下面记录做了什么、怎样验证、哪些没有验证。

## 改动范围

| 改动 | 说明 |
| --- | --- |
| 修改后的验证 | 失败时与修改前对比，只追究新问题；新增“无法验证”“无需检查”两种结论；Ruff 只查改动文件；`.bit-agent/verify.json` 自定义命令和镜像；连续忽略验证提醒时提前停止。见 [VERIFICATION.md](../VERIFICATION.md) |
| 沙箱镜像 | 默认 Python 沙箱的 Dockerfile 随程序分发，缺少时自动构建 |
| 减少确认 | 确认卡片增加“本任务内都批准”（按类别）；删除文件、修改验证配置仍逐次确认 |
| 模型兼容 | 支持 Chat Completions 接口；“测试连接”自动检测接口类型 |
| Docker 提示 | Docker 未安装或未运行时，输入框上方提前提示 |
| 项目说明 | 读取 `AGENTS.md`、`.bit-agent/instructions.md` 交给主 Agent |
| 完成提醒 | 窗口在后台时，任务结束或等待回答弹出系统通知并闪烁任务栏 |
| Git 提交 | 审阅改动里只提交本次任务的文件，可新建分支、生成提交信息 |
| 模型用量 | 任务详情显示整个任务（含子 Agent、验收、摘要）的 tokens，可填价格估算费用 |
| 对话管理 | 搜索（标题、各轮要求和回答）、重命名、删除 |
| 辅助模型 | 可选的便宜模型用于调查、摘要、记忆提炼和提交信息 |
| 外部工具 | 接入用户配置的 MCP Server，按服务确认调用，密钥加密保存。见 [MCP.md](../MCP.md) |
| 错误提示 | 写给用户看的错误（钩子失败、对话还在执行、请填写 API Key 等）原样显示，其余仍是通用提示加诊断编号 |

## 顺带发现并修复的已有问题

| 问题 | 影响 | 修复 |
| --- | --- | --- |
| Windows 文件挂进 Linux 容器后都显示为可执行，Ruff 的 `EXE002` 对每个 Python 文件误报 | 桌面任务的 Python 验证几乎都会失败 | 默认 Ruff 命令忽略 `EXE001`、`EXE002` |
| 默认沙箱镜像从不自动构建 | 新用户第一次验证必然失败 | 随程序分发 Dockerfile，缺少时构建 |
| 运行服务的子进程继承 RPC 标准输入管道 | 便携版里 ripgrep、Docker、Git 等子进程在空闲时卡住，直到下一条请求到来 | 所有子进程显式 `stdin=DEVNULL`；静态检查和 Node 父进程复现测试防止回归 |
| 所有错误在 RPC、Gateway、IPC 三层都被换成通用提示 | 用户看不到“请填写 API Key”之类可以自己处理的原因 | 见上表“错误提示” |
| 审阅弹窗把状态显示成原始值 `unreviewed` | 界面文字 | 显示“待审阅” |
| 继续对话时侧栏标题被最新一句话覆盖 | 与服务端标题不一致；改名后下一轮丢失 | 继续对话时保留原标题 |

## 没有验证的部分

- 真实在线模型（OpenAI 官方、国内服务商）的 Responses / Chat Completions 调用和“测试连接”。
- 真实 Docker 下的 Node 项目验证和前后对比；自定义镜像只用本地已有镜像验证过。
- Windows 系统通知是否实际弹出：便携版没有开始菜单快捷方式时，部分 Windows 版本可能不显示通知（任务栏闪烁不受影响）。
- 带提交钩子、GPG 签名的仓库上的 Git 提交。
- 远程 HTTP MCP Server；需要网络安装的 stdio MCP Server（例如 `npx -y ...`）的首次启动耗时。
