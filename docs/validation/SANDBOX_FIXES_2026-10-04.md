对上一轮 OS 沙箱改动复查后发现的问题逐项处理。所有问题都先在本机用真实官方 SDK 复现，再修复和回归。

## 修改

| 问题 | 复现 | 处理 |
| --- | --- | --- |
| 两个对话同时跑检查，可以写进对方的工作区 | 官方 SDK 的授权挂在同一个 `srt-sandbox` 账户上；A 运行期间 B 的测试写入 A 的工作区成功 | 同一时间只运行一个沙箱命令：Python 进程内排队（排队时间不算进超时），执行器再用命名管道做全机锁（进程退出自动释放）。修复后同样的探针被拒绝 |

| 文档仍是 Docker 时代 | — | 更新 ENVIRONMENT、VERIFICATION、TOOLS、PRODUCT_HARDENING 等文档和给模型的工具说明（`run_tests` 原说明称会自动安装依赖）；删除已无法使用的 `infra/sandbox/python-web` 镜像配方 |

## 没有改的：工作区上一级目录的读权限

尝试过不再开放上一级目录，旁边项目的文件确实读不到了；但 pytest 收集测试时会读取上一级目录本身的属性，工作区在“桌面”“source\repos”这类私有文件夹下时直接报“拒绝访问”。官方 `srt-win` 只提供连同子目录生效的授权，无法只开放目录本身，所以保留原来的授权，并在代码和文档里写明原因。

另外实测：授权上一级目录时，旁边一个 2 万文件的目录让每次运行多花约 4 秒（权限要写到整个子树），空跑的基础耗时约 6 秒。

## Windows 自身权限：加固脚本（方案 A）

`srt-sandbox` 是普通的 Windows 用户。`D:\` 默认给“Authenticated Users”修改权限，并继承到下面所有文件夹，所以沙箱命令可以读写整个 D 盘的其他文件。实测在 `D:\myproject\AI Agent\tmp` 下，工作区外的兄弟目录写入成功。`C:\DevTools`（mise 的 Python / Node）和发布目录（随包 Python 与后端）的权限同样来自继承。

新增 `scripts/harden-sandbox.ps1`（也随发布包分发）：给 `sandbox-runtime-users` 组在这些文件夹上加可继承的“拒绝写入”。演练中修正了两个问题：

1. 拒绝最初挂在 `srt-sandbox` 用户上。工作区的上一级恰好是被加固的目录时，官方 `srt-win` 每次运行都会改写并清理沙箱用户的权限项，拒绝在第一次检查后就消失，外部写入照样成功。改为挂在组上（官方 SDK 自己也用这个组的拒绝保护状态目录）。
2. `icacls /deny` 会自动加入 `SYNCHRONIZE`，沙箱连目录都打不开：pytest 向上查找配置时报 “found no collectors”。改用 .NET 写入，掩码只含 8 项写权限。

最终演练（工作区在被加固目录下一级和两级两种布局，各连续 3 次运行）：工作区外新建、修改、删除、写加固目录根部全部被拒绝；工作区内新建、建子目录、改名、删除正常；pytest（含没有自身配置、需要向上查找的项目）、npm、mypy、ruff 正常；`-Remove` 后权限完全恢复。传播速度约每秒 6000 个文件，本机 D 盘 152 万个文件，预计 4–5 分钟。

真正对 `D:\`、`E:\`、`C:\DevTools` 等执行 `-Apply` 属于修改系统权限，由用户以管理员身份运行。

用户已在本机执行。复查：预览显示 8 个位置全部“已加固”，项目 README、mise 的 Python、发布包内 Python 都带有继承来的拒绝。在 D 盘真实布局下用沙箱连续两次尝试在 `D:\`、`E:\`、项目根目录、`C:\DevTools`、发布目录新建文件，以及修改、删除兄弟项目文件，全部被拒绝，没有留下任何文件；工作区内读写、pytest、npm、mypy、ruff 正常。加固后真实 SDK 集成测试 13 项和真实 OS 独立验收 2 项全部通过。

## 恢复顺序偶发失败（上一轮遗留）

回答由 storage 记录时间，补充 / 改目标由 interaction 记录时间，Windows 上 Python 3.12 的 `datetime.now()` 约 15 毫秒才前进一次，两者可能拿到同一时间，稳定排序把后到的“改目标”排在前面。新增共用的严格递增时钟 `runtime/domain/clock.py`，相同或倒退时向后推一微秒。测试改为固定时钟强制制造并列：旧实现每次都失败（`['replace', 'supplement']`），新实现通过。
