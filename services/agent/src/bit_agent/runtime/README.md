# runtime：把一次对话真正运行起来

上层不用逐个调用压缩器、工作记忆和工具执行器，只使用 `AgentRuntime`。
它是项目内部的运行库，不是需要另外下载的第三方 SDK。

## 先看这条线

```text
桌面发消息
  -> Gateway 接收请求
  -> 本机 Python 进程调用 AgentRuntime.create_task
  -> 根据会话编号恢复历史和工作记忆
  -> run_agent 请求模型、执行工具、压缩过长历史
  -> 每次模型返回和工具完成后保存记录
  -> Gateway 把进度和结果传给桌面
```

## 文件各自负责什么

| 文件 | 大白话解释 |
| --- | --- |
| `__init__.py` | 对外提供 `AgentRuntime` 这个入口。 |
| `bootstrap.py` | 创建默认 SQLite、改动记录、验证适配器并注入业务接口。 |
| `application/service.py` | 管理任务生命周期与连续对话。 |
| `application/ports.py` | 存储、改动记录和项目验证的端口接口。 |
| `application/interaction.py`、`application/capacity.py` | 审批、暂停、取消与执行资源。 |
| `application/delegation.py` | 多 Agent 分工及工具权限。 |
| `domain/` | 产品错误与工具约定。 |
| `infrastructure/storage.py` | SQLite 数据、事务与恢复。 |
| `infrastructure/changes.py`、`infrastructure/verification.py` | 文件改动记录及项目验证适配器。 |
| `transport/rpc.py` | JSON-lines 通信，只依赖异步方法表。 |
| `__main__.py` | 配置、单进程锁、启动和方法表装配。 |

`agent/runtime.py` 仍负责模型与工具的循环。本目录负责外面的会话和生命周期，
不会复制一份模型执行逻辑。Gateway 不再操作这些模块内部的数据结构。

## 为什么有会话编号，也有任务编号

会话编号对应左侧一个对话。你继续发送十条消息，还是同一个会话。
任务编号对应其中一次执行，便于分别查询状态、取消和查看事件。

`create_task` 不传 `session_id` 时新建会话，传入已有编号时继续那段对话。
已有会话绑定工作区，换文件夹需要新建对话，避免把另一个项目的历史混进来。

## 三种模式

| 模式 | 行为 |
| --- | --- |
| `off`，关闭 | 不向模型提供 `delegate_tasks` 工具，主 Agent 自己完成任务。 |
| `on`，开启 | 明确要求主 Agent 优先分工；没有合理分工方式时应说明原因。 |
| `auto`，智能 | 模型在执行中自己决定是否调用帮手，不增加关键词分类器或额外判断模型。 |

每次 `delegate_tasks` 接受 1–3 个只读调查子任务，不限制累计委派批次。
同一主任务最多同时运行 3 个调查子 Agent，跨批调用共享并发名额；超出名额时等待，
完成、失败或取消后释放名额。单个调查子 Agent 仍最多执行 8 轮，并受主任务超时和取消控制。
取消累计批次限制不等于取消主任务的交互轮数和执行时间限制。
子 Agent 只能列目录、读文件、搜索代码，不能运行测试、写文件或继续创建子 Agent。
主 Agent 负责检查调查结论并统一修改。模型是否选择分工不是正确性保证。
旧 `multi_agent/` 的预先规划、工作区副本、结果汇总仍保留，供旧入口和评测使用。

## 数据保存在哪里

Windows 默认 `%LOCALAPPDATA%/BitAgent/runtime`，也可设置 `BIT_AGENT_DATA_DIR`。

```text
runtime/
  sessions.sqlite3       会话、每轮任务、历史记录、工作记忆、事件
  sessions.sqlite3-wal   SQLite 工作时可能产生的配套文件
  sessions.sqlite3-shm   SQLite 工作时可能产生的配套文件
  runtime.lock          防止同一数据目录启动两套互相干扰的服务
  artifacts/            大型工具结果，按任务编号分开
```

没有 TTL，不会一天后自动删除。备份时先关闭应用和后台，再整体复制这个目录；
运行时不能只复制主数据库文件，也不能删除配套文件。
原来的 Redis 数据没有自动迁移，也没有被删除。

## 中断后如何继续

完整记录会追加保存，发送给模型的历史可以另行压缩，两者不是同一份东西。
程序保存最近一次可继续的历史和未验证修改状态，不只保存最终答案。
重新启动时，把上次未结束任务标记为中断，不自动再次执行工具。
如果某次工具调用没有完整结果，会告诉模型先检查现状，不能认为它完全没执行过。

这不是整个操作系统的现场恢复。模型请求、外部程序或文件写入中断后，
不能承诺已经撤销，也不能承诺下一轮自动恢复到某条指令的中间位置。

## 并发和边界

默认不同工作区最多同时运行 2 个主任务。同一个会话不能同时发送两轮任务。
同一个规范化目录的主任务排队，避免两个对话同时覆盖文件。
想同时改前端和后端，优先使用独立 Git worktree；不能仅靠不同对话编号避免文件冲突。
这个目录锁只协调本运行服务，不会阻止编辑器、其他程序或嵌套工作区修改同一文件。

已有模型与工具超时、修改后验证和 Docker 隔离继续保留。
本轮代码修改没有运行测试、类型检查、构建或真实模型调用，运行效果仍待验收。
